# 术语候选提取

找出真正需要统一决策的概念，不把所有高频词、大小写差异或同形词都升级为术语。

## 执行顺序

1. 确认语料范围，用分页批次与句段读取完成声明范围。用户只要样本时固定并说明样本；频次只按实际读取或可靠统计的语料计算，不从小样本外推项目总量。
2. 优先提取专名、产品/玩法/技能名称、关键领域概念及会影响理解的一致性表达。型号、版本或其他有概念价值的数字可以保留。合并前核对是否同一概念；词形相同但语境不同不能强行合并。
3. 对候选所在句段获取批量上下文，纯候选任务使用 `readOnly=true`。先复用已有适用术语、状态、范围和冲突证据；只有证据不足的概念、变体、歧义才补充 `cat_search_terms`，需要历史译法时再查 `cat_search_tm`。不要求每个候选机械重复一遍已充分的查询。
4. 区分“新增候选 / 已有一致 / 已有冲突”。Substring 命中不等于同一概念；未搜到不等于获批准；结果达到返回上限时不能宣称术语库里一定没有其他命中。
5. 译法来源明确区分客户批准、已有术语、TM/Context 参考和模型建议。模型新提出的译名标“模型建议，待确认”，不能标成人工建议、批准译例或既有术语。可根据证据推荐一个优先项，不把所有问题都转交用户。
6. 按影响范围、实际频次和歧义风险排序；不要创建伪精确质量分。默认只提交候选表，不写 TB。用户后续明确采纳具体候选时，才按该范围使用现有术语写入工具；未指定硬约束时不得擅自设 required 或 forbidden，已有冲突也不能静默删除。

## 输出

先说明批次、覆盖量与统计口径，再给候选表：源术语、概念/场景、候选译法、已有状态、实际频次（无法可靠计数则省略）、来源、建议动作。每个候选有可定位的 Segment 或已有术语证据。

无新候选就明确说明，不制造命名工作。只把影响实际译法且证据无法裁决的事项列为待确认，不重复询问用户已经采纳的决定。

## 边界

候选不是批准术语。未获明确授权不调用 `cat_upsert_terms`、`cat_delete_terms`，不修改译文或阶段状态。用户明确只在聊天查看时不生成项目记录。不要把术语规范化扩展成全项目重写。
