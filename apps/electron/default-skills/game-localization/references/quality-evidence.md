# 依据、审校尺度与质量结论

## 1. 先区分错误、可改进与合理变体

错误是偏离本任务的意义、功能、规范或技术要求。可以提出另一种说法，不代表当前译文有错。自然度/声音问题同样可以真实影响成品，不应因“语义差不多”而全部忽略。

修改应能说明具体收益：修正误义、消除歧义、恢复人物语气、符合有效规范、改善实际可读性或修复结构。一般判断可由专业知识支撑，不要求每项必须找到TM或网页。真正依赖客户批准/外部事实时才查对应来源。

“准确”“自然”“合适”要一起看；不能用单一匹配率、QA数量、修改率或唯一参考译文来替代。

## 2. 资料有来源，也有适用范围

当前Source与客户明确需求共同定义任务；项目术语、SG、批准例句、旧TM、截图和一般行业惯例各有职责。没有全世界通用的“最高TM分永远胜出”“最新文件永远覆盖一切”排序。

先核是否同版本、同概念、同文本功能和同批准范围。条目来自本轮自己回写，就不能作为独立客户批准依据。普通历史参考可辅助判断，不要求先找到一个完全相同句子才敢修语法。

需要完整规范基线时，不只读第一页或最新增量。完整基线建立后按版本复用；图片示例中的规范不能被文件名代替。机器receipt仅证明内容被提交过，不证明理解或批准。

## 3. 一致性不是所有同词都同译

同一概念、同功能和同版本宜一致；不同词义、角色声线、语体或运行场景可不同。对重复/近重复内容先利用现有检索缩小范围，再比较差异，不复制其它句的数值、条件与对象。

同源也可能分不同UI位置；仅文本相同不代表同任务身份。术语表定义词形，不自动决定句中大小写或全部语法变体；明确客户case规则除外。

## 4. 结构与语言的边界

标签、变量和换行是内容的一部分，不是可在末尾随意补回的噪声。保证实际运行身份、配对、样式作用范围和字符串格式有效。

但目标语允许改变变量顺序，复数类别可能与源语言不同；客户已规定的目标语语法代码可能源文没有。按具体格式与项目能力验证，不能用所有token完全相同作无限通用规则，也不能以“语言自由”放过未知结构。

自动数字/词形/标点警报是线索，须结合意义和项目规范。明确身份/版本/锁/编码错误属于技术保护，不能靠语言理由绕过。

## 5. QA和状态如何报告

已判断误报与平台成功保存忽略不同；已确认句段与已完成工作不同；工具成功与网站保存不同；Stage完成与语言质量验证不同。

QA只覆盖运行的配置与范围。实际游戏里的布局、配音、UI拼接和交互需要相应环境，不凭文本检查说LQA已通过。先前有效检查可复用，修改影响的范围再查；不为了零警报把问题全忽略。

## 6. 例外处理

局部证据未决只阻断依赖它的结果。保留来源、问题和候选，继续其它内容。确定不能执行的权限/客户决定才交给用户；不要把普通专业建议伪装成必须由用户回答的问题。

发现已完成结果有真实问题时修正并记录影响，不为保护旧结论而忽略，也不自动重跑所有历史。没有新依据就不要在两个合格表达之间来回修改。
