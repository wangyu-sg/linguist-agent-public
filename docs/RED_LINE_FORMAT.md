# 项目红线编写规范 (Red-line authoring format)

本文说明**如何编写一份能被 Linguist Agent 检索并引用的项目红线文件**。红线指项目方下达的、必须遵守的硬性翻译约束(禁用译法、口吻锁定、占位符规则、合规禁区等)。

## 为什么格式有硬要求

红线文件以 `style_guide` 角色导入后,会被**逐行切块**成可检索的 asset block:

- 对 `.md` / `.txt`,每个 block 的 `blockId` = `相对路径:行号`(一行一块)。
- block 通过 `asset_block_search` / `asset_read` 检索(lexical bigram-Dice + vector/hybrid)。
- 命中的红线按 **style_guide 权威 (tier 90)** 参与排序——高于 model judgment,低于 termbase/glossary 与 locked 行。

直接后果:**agent 一次只能命中"一行"。** 如果一条红线的关键信息分散在多行、或依赖上文标题/前一行才能读懂,检索时就会被切碎,命中片段不自包含,红线等于失效。

## 编写规则

1. **一条规则一行(或一行表格)。** 不要把多条规则塞进一个段落。
2. **自包含。** 每行必须独立可读:写清"规则 + 适用范围 + 违反后果",不要用"同上""见上一条""如前所述"。
3. **带足关键词。** 该行里要出现能被搜到的术语/原文词/角色名,否则检索匹配不到。
4. **不靠标题继承语境。** Markdown 标题不会和正文同块;标题里的限定词要在每条红线里重复写出。
5. **后果用缺陷等级标注。** 用 `L0`–`L4` 标明违反后记几级缺陷,和《通用缺陷等级》口径对齐,便于 review 阶段直接套 severity。

## 字段格式

推荐管道符(`|`)三段式,每行一条:

```
规则类型 | 规则内容（含原文/术语/角色名等可检索关键词） | 适用范围，违反后果
```

示例:

```
禁用译法 | gain 一律译"获得"，obtain 一律译"取得"，二者不可互换 | 全项目术语，违反记 L1
口吻锁定 | 角色"老张"固定自称"老子"，不可换成"我" | 角色人设，违反记 L1
占位符   | {playerName} 不可翻译、不可加空格、不可调整大小写 | 运行时变量，违反记 L0
合规禁区 | 不得出现真实国家/地区政治表述 | 全项目合规硬雷，违反记 L0
长度约束 | 主菜单按钮 zh-CN 不超过 6 个全角字符 | UI 按钮，违反记 L2
```

也可用 Markdown 表格(每行同样自包含),效果等同——只要保证一条规则不跨行。

## agent 怎么用

- 翻译/审校时,涉及术语、口吻、占位符、合规的判断,agent 会先 `asset_block_search` 检索红线,命中即按 tier 90 引用并遵守。
- 红线被引用时,`evidenceSources` 里会带上命中的 `blockId`(`相对路径:行号`),可回溯到具体哪一条。
- 红线 ⚠️ 不会凌驾于 locked 行、termbase/glossary 之上;若红线与更高权威冲突,agent 会挂 `query`/`needs_review` 交人决策。

## 维护

- 红线变更后,改动的行号会变,`project_refresh` 后重新切块即可,无需手工同步 blockId。
- 红线文件越精炼越好:一条规则反复命中,胜过一大段没人能整段命中的说明。
